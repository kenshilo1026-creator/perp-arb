# 價差執行逐步修改與回放結果

2026 年 10 月 28 日，前五個階段以 `64ca300` 為修改前基準，已保存於 commit `2f4e543`。第六階段以 `2f4e543` 為基準，修改尚未提交；沒有送出實盤訂單。`variational-v1/` 未修改。

## 比較方法

每個階段都執行同一份 `scripts/replay_spread_execution.py`，使用原本相同的交易參數和事件時間線。回放固定使用原來 15 秒新鮮度設定，避免後來調整預設值使前後案例不可比。它驅動實際 Engine，使用暫存狀態檔和模擬交易所，完全離線。

這是 **合成事件回放，不是歷史市場收益回測**。事件每 10 ms 推進；模擬交易所不計網路、撮合等待、隊列或費用。「0 ms」代表同一模擬時間點處理，不能解讀為實盤零延遲或已達到 100 ms 內跨所成交。

## 第六階段的對沖等待協調

原本 `ensure_hedged` 等待送單及確認，會阻塞引擎處理下一筆 Maker 成交和危險掛單。新版由同一個協調流程更新狀態；對沖、撤單及 REST 查單各自等待 I/O，結果由協調流程逐一記錄。尚未確認的對沖保留為 `PENDING_SUBMIT`，避免把它當成沒有送過而重複下單。

新增情境在 0 ms 成交 0.005，第一筆對沖回覆延至 500 ms；100 ms 時 Maker 累計成交增至 0.01，對沖報價從 2000 惡化至 2010。使用同一份回放程式，分別載入已提交的 `2f4e543` 引擎與目前引擎：

| 指標 | `2f4e543` | 第六階段 |
| --- | --- | --- |
| 新增成交至記入狀態 | 400 ms | 同一模擬時間點 |
| 不利行情至撤單確認 | 400 ms | 同一模擬時間點 |
| 對沖數量 | 0.005 加 0.005 | 0.005 加 0.005 |
| 最終殘餘曝險 | 0 | 0 |

這個情境的撤單回覆沒有模擬網路耗時，因此同一時間點撤單不代表實盤即時撤單。原有四個情境結果保持不變。此步改善等待期間的處理能力，沒有縮短交易所本身的 500 ms 回覆。

新增測試也驗證：慢撤單不阻止繼續記錄成交及下一筆已知曝險的對沖、私人 WS 確認等待不阻塞 Maker 事件、慢 REST 不阻止撤單、只有 REST 的 Maker 仍按既有間隔更新、重複修復呼叫共用同一筆送單、停止程式時等待已送交易並保存結果，以及未知對沖不重送。未知案例保留真實的 0.008 殘餘曝險並暫停，不會假裝歸零。

新增成交仍須等前一筆對沖有確定結果才會補送；安全掛單在這期間仍可能繼續成交。後續若要在未知回覆期間也平行對沖增量，需要更完整的訂單識別、在途數量與方向協調。本步沒有改寫一般掛單提交、普通重新掛單或雙 Taker 提交的整個生命週期，也沒有新增其他交易所的私人 WS。

## 目前能力與限制

- 私人訂單更新目前接通 **Aster**。Hyperliquid、Lighter 等在此策略仍沿用原有確認路徑；不宣稱已替全部交易所完成私人 WS。共享 Aster adapter 的同時啟動有鎖，避免建立重複連線；執行期間斷線會保留 REST，尚未新增持續背景重連。
- 已確認的累計成交只按新增加部分對沖。回覆不明的訂單不盲目重送；未確認安全撤單時不增加新掛單。跨所交易仍不具原子性。
- 公共行情失效時可用已快取價格作數量／帳務參考，但不把它當實際成交價或 IOC 限價。交易所仍可能拒單；最小下單量及 dust 限制仍存在。
- 預設行情上限為 1 秒、來源至接收差上限 0.5 秒、未來時間容忍 0.25 秒；**已有設定檔的明確數值保留**。更嚴格的上限可能減少下單和增加撤單，後續需依實際行情頻率與時鐘品質校準。
- `hedge_dispatch` 記錄本地收到 Maker 成交至對沖 dispatch 的耗時；`hedge_confirmation` 記錄 dispatch 至確認的耗時。兩者都不是兩所的實際成交時間差。沒有來源時間時輸出 null。
- 本輪沒有新增主動吃單的 lead-lag 策略、購買資料服務或改寫 Rust。這些項目需要足夠逐筆資料與樣本外成本驗證，不能由四個合成案例決定。

以示例 ETH 的 Aster／Hyperliquid 配對，只讀公開行情 20 秒。檔案為 `data/market_replays/2026-10-28-eth-smoke.jsonl`，包含設定、逐筆深度、來源時間、本地 wall-clock／monotonic 接收時間、連線狀態與結尾計數。

| 來源 | 記錄數 | 接收時間減來源時間最小值 | 最大值 | 平均值 |
| --- | --- | --- | --- | --- |
| Aster | 94 | 48 ms | 687 ms | 約 131.1 ms |
| Hyperliquid | 4 | 314 ms | 480 ms | 365.25 ms |

錄製佇列丟失數為 0。這些是短樣本中的來源至接收時間差，**包含時鐘偏差、發布及傳輸，不是網路 RTT 或撮合延遲**。Hyperliquid 只有 4 筆，不能據此計算可信的尾部表現或推出誰領先。

錄製工具不載入 `.env`、不建立執行 adapter、不送訂單；檔案採獨佔建立，避免覆寫既有錄製。資料寫入移到背景執行緒；佇列溢位會報告不完整而非默默忽略。

## 重現指令

```powershell
python scripts/replay_spread_execution.py --output docs/benchmarks/spread-execution-rerun.json
python scripts/record_spread_market.py --config configs/spread_strategy.example.json --seconds 3600 --output data/market_replays/eth-session-01.jsonl
```

第二行是後續錄製指令，本次沒有啟動這個一小時工作。先錄到足夠不同波動與交易時段的資料，再做領先訊號、條件滑點及撤單成功率回放。分鐘 K 線不足以驗證毫秒套利，這次的 20 秒錄製也不足以作收益結論。
